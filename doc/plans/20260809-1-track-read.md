# Plan: Fast Playlist Track Read

## Summary

Selecting a playlist reads its complete ordered track URI list from
`GET /v1/playlists/{id}/tracks` and shows the count on the page. Reads are
fast for large playlists: URI-only field filtering, the endpoint's maximum
page size, and bounded-concurrency parallel page fetches computed from the
playlist total, guarded by a snapshot check that fails the read if the
playlist mutated mid-flight. The loaded list is held in page state as the
attachment point for caching (the follow-up plan) and shuffling.

## Problem

Selecting a playlist records `{id, name}` and renders a message; no track
data is ever read. Every product goal -- caching membership, generating an
order, writing batches -- needs the ordered URI list first.

Speed is the binding constraint, not just capability. The existing listing
pattern -- sequential `next`-cursor following -- would cost a 10,000-track
playlist 100 serial round trips; at mobile latencies that is tens of
seconds per read. Offset paging makes the pages independent, so after one
response reveals the total the remaining pages can be fetched concurrently.

Parallel reads of a mutating playlist can interleave pages from different
playlist versions and silently assemble a corrupted order. That corruption
would be invisible until a later shuffle writes the wrong list back, so the
read must detect it and fail, not guess.

## Scope

In scope:

- Read the selected playlist's ordered track URIs with `fields`-filtered,
  offset-addressed pages fetched by a bounded-concurrency pool.
- Pin `snapshot_id` before the read and verify it unchanged after; fail the
  read on mismatch or on an item-count mismatch against the reported total.
- Render loading, loaded-count, and failure states in a new `track-status`
  element; hold `{id, snapshotId, uris}` in module-scope page state.
- New pure logic and direct tests; harness coverage for the wired flow; the
  new page marker in the Go page test.
- Update the integration and application-model architecture pages and the
  README status.

Out of scope:

- Caching, snapshot comparison across visits, and difference reporting: the
  follow-up plan `20260809-2-track-cache.md`.
- Shuffle generation and any playlist write.
- Track metadata (names, artists). Only URIs are read, per the product goal
  of never downloading full metadata.
- Retry, backoff, and `Retry-After` handling; the fail-fast posture stands.
- Rate-limit budgeting or throttling beyond the fixed pool bound. Spotify's
  limits are unpublished; live validation records observed behavior on a
  large playlist, and any governor is designed from that data, not ahead of
  it.
- On-demand token refresh. Tokens are refreshed only during `initialize()`;
  a selection on a page left open past expiry surfaces a read failure and a
  reload refreshes. This preserves the single-refresh-path invariant.
- Request cancellation. Selecting during a load is prevented instead.

## Design

**Read protocol.** Three phases, each a fail-fast invariant:

1. Pin: `GET /v1/playlists/{id}?fields=snapshot_id` records the version
   being read.
2. Fetch: page 0 of `/v1/playlists/{id}/tracks` with
   `fields=limit,total,items(track(uri))` and the documented maximum
   `limit=100`. The response echoes the server-enforced page size and the
   authoritative total, so the remaining offsets are computed from server
   facts, never from documentation assumptions. Remaining pages are fetched
   by a pool of at most 6 concurrent requests and assembled by offset.
3. Verify: the summed raw item count must equal the total, and a second
   `snapshot_id` fetch must equal the pin. Any mismatch discards the read
   and renders "changed while loading; select it again".

A total above Spotify's 10,000-item playlist cap is an error, mirroring the
listing's bounded-paging rule.

**Every track URL is constructed, never followed.** Offset URLs are built
locally against the fixed API origin with the playlist id URI-encoded --
Spotify-supplied ids are third-party strings. Track reading follows no
server-supplied cursor at all, so the bearer token cannot be steered
off-origin by a response; the listing's cursor guard has no analogue here
because there is no cursor.

**Page reading is pure.** `web/pure.js` gains the playlist-metadata reader,
the track-page reader (raw item count plus URIs, skipping items without a
string `track.uri`, as the listing reader skips null placeholders), the
offset-URL builder, and the cap check. The raw count includes skipped items
so the completeness check compares like with like. `web/app.js` owns the
pool, the three-phase orchestration, and rendering.

**Concurrency is a constant, not a knob.** `maxConcurrentTrackRequests = 6`
in `web/app.js`. A pool wide enough to matter, narrow enough not to invite
`429`s; a `429` still fails the read under the standing posture. The pool
dispatches nothing further after its first failure, so a failed read costs
at most the requests already in flight.

**One load at a time.** Selecting disables the playlist buttons until the
read settles, then re-enables them. This prevents interleaved loads and
double-click request storms without cancellation machinery. Re-selecting
the already-loaded playlist re-reads; deduplication is the cache plan's
job.

**Failure scope.** A failed read -- HTTP error, torn snapshot, count
mismatch -- clears `loadedTracks`, renders the failure in `track-status`,
and touches nothing else: the listing, selection, and stored token remain
intact, consistent with the rule that only token-endpoint evidence
classifies authorization.

## Affected Components

- `web/pure.js`: playlist-metadata reader, track-page reader, offset-URL
  builder with the id encoding and the 10,000-item cap.
- `web/app.js`: the pin/fetch/verify orchestration, the bounded pool,
  `loadedTracks` page state, button disabling, and the `track-status`
  states, wired from `selectPlaylist`.
- `web/index.html`: add `<p id="track-status" ... hidden>` beside the
  playlist status line.
- `web/pure_test.js`: direct cases for the three new readers/builders --
  URL construction and encoding, cap rejection, malformed payloads, null
  and URI-less item skipping, raw-count semantics.
- `web/app_test.js`: extend the fake `fetch` to serve the playlist pin and
  offset pages; cases for assembly in offset order from out-of-order
  responses, the torn-snapshot failure, the count-mismatch failure, a read
  failure leaving listing and token intact, buttons disabled during load,
  and an empty playlist rendering a zero count.
- `main_test.go`: add the `track-status` marker to the page test.
- `doc/architecture/integration/SPOTIFY_INTEGRATION.md`: the two new
  endpoints, the echoed-limit protocol, the parallel bound, and the
  constructed-URL-only property.
- `doc/architecture/browser/APPLICATION_MODEL.md`: selection now loads
  tracks; the attachment point becomes the loaded track list (planned
  marker moves with it).
- `README.md`: status gains track reading; playlists are still never
  modified.

5. Update the two architecture pages and the README status.

## Validation

```sh
gofmt -l main.go main_test.go
go test ./...
go vet ./...
node --check web/pure.js
node --check web/app.js
node --test web/pure_test.js web/app_test.js
git diff --check
! grep -nE 'document|window|fetch|localStorage|sessionStorage|crypto|location|history' web/pure.js
```

The JavaScript tests must prove: pages assemble in offset order even when
responses complete out of order; a snapshot change or short page count
fails the read and preserves listing, selection, and token; the pool never
exceeds its bound (observable from the harness's request log versus
resolution order).

Live validation -- a real account with a multi-page playlist, recording
elapsed time, the echoed limit, and whether any `429` occurs -- is
performed only with explicit user direction, per `AGENTS.md`. That record
is the evidence base for any future rate-limit governor. Deployment follows the private
runbook on explicit direction and may ship together with the follow-up
cache plan.

## Success Criteria

- Selecting a playlist renders a loading state and then the exact track
  count; the ordered URIs are in page state.
- Remaining pages are requested concurrently (bounded at 6) after page 0,
  and assembly order is by offset, proven by test.
- A mid-read playlist mutation or short read fails loudly with nothing
  cached in page state and nothing else disturbed.
- No server-supplied URL is fetched during track reading.
- An empty playlist renders a zero count without error.
- The purity grep stays clean and every prior test passes unmodified.
- The integration and application-model pages and the README describe the
  new behavior.
